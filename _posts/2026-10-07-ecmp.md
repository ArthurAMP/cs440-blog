## Key Idea

Data centers are often built with equal-cost multi-path (ECMP) routing. Thus, a flow starting from a node would have many options for paths. The common approach is to hash the flow and associate the hash to a path. 

As these flows can fail, prior work (PRR, PLB) would change a header on the flow and rehash it so it lands on a random path. This, however, doesn't guarantee it would be a different path, for it could be hashed to the same path. Plus, if you need any sort of precision in selecting a path (for instance, localizing a failure) you have no way of doing it with the prior state-of-the-art. 

This paper solves this problem by using a feature that is underutilized: ECMP groups. The vast majority of switches use a very small fraction of the space allocated by hardware providers. They developed a compiler that builds a forwarding table as groups for the hash to index into. Two main types of groups were created. One of them are groups that are just Group 0 but offset and wrapped around, which are useful for avoiding repeating a path (as the flow will hash to the same position as it would in a different group, and the offset guarantees that it is a different path) and to do load balancing. The other are groups that only contains a specific next hop. Those are useful to have precise traffic control, as you will be able to choose the hop you wanna take through the group selection bits.

## Critique

The idea is immediately convincing almost by construction. It dodges the pitfalls of randomized flow hashing cleanly, and it is clearly compatible with randomized flow ECMP deployments. I also liked how the use cases were clearly shown both in the paper and in the presentation.

My main critique is to the evaluation section. Reading it with the mindset of reproducing results, these experiments are somewhat underspecified. Sentences like "Most experiments in § 5.1 and § 5.2 are done using the NS3 simulator" is most of what we get and that is almost zero information. This also make their comparisons somewhat suspicious, as there is very little detail on how PRR and PLB were setup. I'm also surprised they wouldn't run the network experiments with topologies other than #12. 

## Connections

While I cannot think of a direct connection, I wonder whether the evaluation could have been pushed further if the authors had created a adversarial flow generator and stress tested P-ECMP, sort of [how Raha works](/cs440-blog/2026/09/30/islands-and-peninsulas/).
