## Key Idea

One of the ways one can deanonymize onion hosts is by owning a lot of relays, and then spamming the website with connections until the entry node is only one hop away from an adversary-owned relay. From that point, you might be able to get her IP address through legal action against the entry node provider. Another common way is by leveraging the website uptime is a good proxy for host uptime, so localized network/electricity shutdowns, especially if they happen often, would narrow down the location of the host.

The solution they propose is offloading the application hosting to someone that would be willing to host the application for you. They would run it in a trusted execution environment (for the prototype, SGX), which would guarantee that the host wouldn't be able to make changes to the website without being noticeable by a certificate checker. They also claim that the operator wouldn't be able to snoop into uploaded data, and they wouldn't be able to distinguish publisher from reader. 

## Critique

This is a good idea. It is hard to criticize because there are so many unavoidable flaws. For one, the risk fully shifts to the vault operator; the main attack vector is not fixed. There is also the problem with using certificate checkers when using Tor in the first place, as addons are not recommended for deanonymization risk. Thus, I will focus mainly on methodology and accuracy of claims. 

My main qualm with the paper is the evaluation. It is almost entirely parallel to the central claim, and the part that is actually talking about the deanonymization risk is hardly an evaluation. And I understand that this extremely hard to evaluate, but they could have spun a private network running Tor code and attempt some of these attacks without affecting the real onion network at all.

The second thing is that I really don't like how they discount side channel attacks from the threat model. They equivocate the side channel risk in this scenario with the risk for estabilished enclave providers. That is very incorrect, as estabilished providers have a reputation to maintain. The vault providers are way sketchier and they have complete physical access to the node hosting your application. This is the threat model equivalent of borrowing money from a loan shark, and pointing out the existance of banks when arguing for that not being a dangerous idea. Plus, "vendors promptly patch side channels" falls apart when we are talking about physical fault injections. Intel can't really patch physical clock glitching, and people have done it against up-to-date SGX. In fact, [VoltPillager] still supposedly works, and [Intel reportedly](https://securityaffairs.com/111033/hacking/voltpillager-attack-intel-sgx.html) called physical attacks out of scope. You know who has full physical access to the motherboard and could not care about their reputation? Vault providers.
